  - 200 件貼圖（每件 1 張圖，其中 40 件屬於項目「春季選題」）。

## 方法與「視窗隱藏」對數字的影響

| 指標 | 怎麼量 | 隱藏視窗下可信嗎 |
| --- | --- | --- |
| 幀間隔（frame time） | 頁面內記錄每個 `requestAnimationFrame` 的時間戳 | **節奏可信，上限不同**：隱藏視窗由合成器自己的 BeginFrame 以 **60 Hz** 驅動（閒置時間隔中位數 16.7 ms）。螢幕上若是 120 Hz ProMotion，每幀預算是 8.3 ms，這裡量不到。 |
| 掉幀 | ① rAF 間隔超過 1.5 個 vsync，就計入缺少的幀數 ② trace 中的 `DroppedFrame` | ① 可信，代表主執行緒或合成器沒交出幀 ② 只能參考：隱藏視窗沒有真正的顯示呈現，合成器的「掉幀」判定和螢幕上不同 |
| 長任務 > 50 ms | `PerformanceObserver('longtask')` | **可信**：主執行緒的 JS／樣式／排版工作與視窗是否可見無關 |
| 長動畫幀（LoAF） | `PerformanceObserver('long-animation-frame')`，含 scripts、renderStart、styleAndLayoutStart | **可信**，可以分辨慢的那一幀是 JS、排版還是在等待 |
| CPU 分解 | CDP `Performance.getMetrics` 前後差：Script、Layout、RecalcStyle | **可信** |
| GPU 光柵、合成上屏 | 無 | **量不到**：視窗不上屏就沒有真正的呈現。GPU 端成本可能被低估 |

- 結論：主執行緒的成本（JS、樣式、排版、長任務）是最可信的部分。幀節奏只在 60 Hz 下有意義。
- 120 Hz 的實際體感、GPU 端成本：`NOT_VERIFIED`。要驗證就必須把視窗放到螢幕上，依規定不做。
- 互動方式：
  - 滾輪：Playwright 的 `mouse.wheel`，每 16 ms 一次，每次 240 px。
  - 點擊與拖曳：經 CDP 注入。
  - 每項互動結束後多錄 400 ms，讓動效（上限 `slow` 320 ms）跑完。

## 判讀

- **整體流暢**：
  - 4 種互動在 4 輪中**都沒有長任務**。
  - 幀間隔中位數都是 16.7 ms，p95 都 ≤ 18.6 ms，也就是 60 Hz 的每一幀都準時。
  - 300 件資料下，篩選、全選、拖放都沒有掉幀。
- **偶發的單一長幀（150–187 ms）**：
  - 出現在捲動，有一次在批量刪除。大約一半的輪次會出現，**動效關閉時也有**（183 ms）。
  - LoAF 的內容：`blocking 0`、沒有任何 script、render 與 style／layout 都 < 1 ms。也就是說，**那一幀主執行緒是閒的**，時間花在等下一個 BeginFrame。
  - 推論（未驗證）：卡在 renderer 主執行緒之外，例如合成器、GPU 行程或圖片解碼。這可能是隱藏視窗特有的現象。
  - 這不是 QC-065 動效造成的：動效關閉也會出現，而且主執行緒在那一幀沒有工作。
  - 螢幕上是否感覺得到：`NOT_VERIFIED`。
- **沒有發現明確的卡頓缺陷**，所以沒有開 bug。建議使用者安裝後，在真實螢幕上快速捲動 200 件以上的作品庫，看是否偶爾頓一下。

## 附帶發現（功能，不是效能）：作品庫最多只顯示 200 件

- `apps/mac/src/renderer/LibraryPage.tsx` 只用 `client.works.list({ limit: 200 })` 載入一次，**沒有分頁或「載入更多」**。
- 實測：種子 300 件，作品庫只顯示 200 張卡片，是最新的 200 件。
  - 「貼圖」篩選只顯示 100 件，實際有 200 件。
  - 其餘 100 件在作品庫看不到，篩選計數也不包含它們。
- 使用者作品超過 200 件時，舊作品會從作品庫「消失」（資料還在）。
- 已在交付訊息中回報總監，由總監判斷是否開票。
